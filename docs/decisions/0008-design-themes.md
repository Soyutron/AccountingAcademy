# 0008. 配色・書体・形を切り替え可能な「テーマ」として定義し、既定は「街の小さな会社」にする

日付: 2026-11-08
状態: 採用(ユーザー決定2026-11-08。詳細は`docs/design-system.md`。実装2026-11-08)

## 背景
UIがshadcn/uiのneutralプリセットのままで、ブランドを示す色・形・書体がなく、画一的に見えていた。
5要素の色はTailwindの既定色で、状態色(正解 = emerald、ヒント・不正解 = amber、エラー = rose)が収益・費用・負債の色と衝突していた。
4つのデザインコンセプト(A藍と朱 / B帳簿用紙 / Cワークベンチ / D街の小さな会社)を比較した。比較の時点では、5要素の色相を動かさずに済み、ブランド展開しやすいAを推奨した。
一方、デザインの好みは人によって分かれ、プロジェクトはオープンソースのコミュニティを重視する。1つに絞るより、選べて増やせる形のほうがビジョンに合う。

## 決定
- **テーマ機構を導入する。** テーマはCSS変数の束(意味・要素・状態・形・書体の5層)で、1テーマ = 1つのCSSファイル(ライト・ダークの2ブロック)。レイアウト、ペイン構成、コンポーネントの構造、5要素の記号、動きの規則はテーマで変えない。
- **既定テーマはD「街の小さな会社」。** 比較時の懸念(主色の緑が収益と、はちみつ色が費用と衝突)は、収益を黄緑に寄せ、はちみつ色を状態に使わない差し色に限ることで避ける。
- **A〜Cも同梱し、ヘッダーから切り替えられる。** 選択はlocalStorageに保存し、DBには置かない。ライト・ダークはテーマと独立した設定(自動 / ライト / ダーク)にする。
- **全テーマ共通の規則を置く。** 5要素の色相系統の固定、状態は形で分ける(ずれ・エラーは面を塗らない)、コントラストAA、書体はフォント登録簿から選ぶ。必須トークンとコントラストはテストで検査する。
- **利用者がテーマを作って共有する仕組みは、作る人が現れてから足す。** まずはリポジトリへのPRでテーマを受け取る。書き出し・読み込み、ギャラリーには開始条件を置く(design-system.md 7章)。

## 影響
- `globals.css`のトークンを5層に再編し、`src/lib/elements.ts`のクラス名を要素トークンに置き換える。状態色を要素色から分離する。未定義だった`--font-mono`の参照を直す。
- `src/themes/`にテーマ4本、登録簿、フォント登録簿、検査テストが入る。ヘッダーにテーマ切替が付く。
- `docs/ide-design.md` 8章の色の記述は「色相の系統」に改め、具体的な色はテーマに委ねる。`docs/visual-guidelines.md`のイラスト再着色の色は`--brand-accent`に読み替える。
- 日本語Webフォントが増える(BIZ UDPGothic、Zen Maru Gothic、Zen Kaku Gothic New、Zen Old Mincho、M PLUS 1 Code)。next/fontのサブセット化により、ダウンロードされるのは使用中のテーマの分だけ。`docs/assets-ledger.md`に記録する。
- 実装は「1単元で試してから広げる」方針に合わせ、既定テーマをIDE 1画面で調整してから全ページに展開し、その後に残り3テーマを整える。

## 検討した別案
- **A「藍と朱」を単一テーマとして採用**: ブランド展開は最も強いが、好みの分かれる見た目を固定することになり、テーマ貢献という入口を作れない。
- **テーマごとにUIを作り分ける(レイアウトや装飾まで変える)**: 表現の幅は広いが、保守対象が線形に増え、E2Eと図解コンポーネントをテーマの数だけ検証することになる。不採用。
- **ライト・ダークを別テーマとして扱う(VS Code方式)**: テーマ数は減るが、OSのダーク設定に追従できず、利用者が2回選ぶことになる。不採用。
