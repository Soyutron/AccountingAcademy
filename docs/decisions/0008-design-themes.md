# 0008. 配色・書体・形を切り替え可能な「テーマ」として定義し、既定は「街の小さな会社」にする

日付: 2026-11-08
状態: 採用(ユーザー決定 2026-11-08。詳細は `docs/design-system.md`。実装 2026-11-08)

## 背景
UI が shadcn/ui の neutral プリセットのままで、ブランドを示す色・形・書体がなく、画一的に見えていた。
5 要素の色は Tailwind の既定色で、状態色(正解 = emerald、ヒント・不正解 = amber、エラー = rose)が収益・費用・負債の色と衝突していた。
4 つのデザインコンセプト(A 藍と朱 / B 帳簿用紙 / C ワークベンチ / D 街の小さな会社)を比較した。比較の時点では、5 要素の色相を動かさずに済み、ブランド展開しやすい A を推奨した。
一方、デザインの好みは人によって分かれ、プロジェクトはオープンソースのコミュニティを重視する。1 つに絞るより、選べて増やせる形のほうがビジョンに合う。

## 決定
- **テーマ機構を導入する。** テーマは CSS 変数の束(意味・要素・状態・形・書体の 5 層)で、1 テーマ = 1 つの CSS ファイル(ライト・ダークの 2 ブロック)。レイアウト、ペイン構成、コンポーネントの構造、5 要素の記号、動きの規則はテーマで変えない。
- **既定テーマは D「街の小さな会社」。** 比較時の懸念(主色の緑が収益と、はちみつ色が費用と衝突)は、収益を黄緑に寄せ、はちみつ色を状態に使わない差し色に限ることで避ける。
- **A〜C も同梱し、ヘッダーから切り替えられる。** 選択は localStorage に保存し、DB には置かない。ライト・ダークはテーマと独立した設定(自動 / ライト / ダーク)にする。
- **全テーマ共通の規則を置く。** 5 要素の色相系統の固定、状態は形で分ける(ずれ・エラーは面を塗らない)、コントラスト AA、書体はフォント登録簿から選ぶ。必須トークンとコントラストはテストで検査する。
- **利用者がテーマを作って共有する仕組みは、作る人が現れてから足す。** まずはリポジトリへの PR でテーマを受け取る。書き出し・読み込み、ギャラリーには開始条件を置く(design-system.md 7 章)。

## 影響
- `globals.css` のトークンを 5 層に再編し、`src/lib/elements.ts` のクラス名を要素トークンに置き換える。状態色を要素色から分離する。未定義だった `--font-mono` の参照を直す。
- `src/themes/` にテーマ 4 本、登録簿、フォント登録簿、検査テストが入る。ヘッダーにテーマ切替が付く。
- `docs/ide-design.md` 8 章の色の記述は「色相の系統」に改め、具体的な色はテーマに委ねる。`docs/visual-guidelines.md` のイラスト再着色の色は `--brand-accent` に読み替える。
- 日本語 Web フォントが増える(BIZ UDPGothic、Zen Maru Gothic、Zen Kaku Gothic New、Zen Old Mincho、M PLUS 1 Code)。next/font のサブセット化により、ダウンロードされるのは使用中のテーマの分だけ。`docs/assets-ledger.md` に記録する。
- 実装は「1 単元で試してから広げる」方針に合わせ、既定テーマを IDE 1 画面で調整してから全ページに展開し、その後に残り 3 テーマを整える。

## 検討した別案
- **A「藍と朱」を単一テーマとして採用**: ブランド展開は最も強いが、好みの分かれる見た目を固定することになり、テーマ貢献という入口を作れない。
- **テーマごとに UI を作り分ける(レイアウトや装飾まで変える)**: 表現の幅は広いが、保守対象が線形に増え、E2E と図解コンポーネントをテーマの数だけ検証することになる。不採用。
- **ライト・ダークを別テーマとして扱う(VS Code 方式)**: テーマ数は減るが、OS のダーク設定に追従できず、利用者が 2 回選ぶことになる。不採用。
