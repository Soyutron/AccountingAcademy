# 開発方針とロードマップ(v2)

更新日: 2026-11-08
状態: 採用(ユーザー決定 2026-11-08)。ビジョンは `docs/vision.md`、公開とライセンスは ADR 0007。
マイルストーンの順序は固定し、各マイルストーンの中身は着手時に見直す。v1 からの変更は 3 章。

## 1. 開発方針

1. **学習体験の検証を最優先する。** 各マイルストーンは「人が触れる状態」で終える。作って終わりにしない。
2. **縦に薄く、横に広げる。** 新しい課題の種類や機能は 1 単元で試し、効果を確かめてから量産する。
3. **content as code を守る。** コンテンツはビルドで検査し、E2E が全単元を自動で解く。これは量産の仕組みであると同時に、外部からの貢献(PR)を安全に受け取る仕組みでもある。コンテンツを DB に移さない。
4. **会計 IDE の独自性に投資する。** 既存教材の再現(動画、四択、暗記カード)には投資しない。迷ったら「操作して結果を見る」形にする。コミュニティ機能より先に、人が残る理由を作る。
5. **個人で始め、引き継げる形を保つ。** 保守対象を増やさない。インフラは CLI とスクリプトで再現できるようにし、判断は ADR に残す。開発者 1 人がいなくても続く構造(docs、Skills、テスト、貢献ガイド)を優先する。
6. **測って直し、測った結果を開く。** 回答ログから誤解の分布と初回正答率を見て解説と誤答パターンを改善する。集計は匿名化して公開し、貢献の入口にする。
7. **コミュニティ機能は利用者がいてから開く。** Q&A・記事・コンテストには開始条件(利用者数や報告数)を数値で置き、満たすまで作らない。空の掲示板を作らない。

## 2. 段階とマイルストーン

ビジョンの 5 段階にマイルストーンを対応させる。規模感は個人開発 + AI エージェントの前提での目安。日付は置かず、順序と完了条件で管理する。

| 段階 | マイルストーン |
|---|---|
| 1 学習体験の確立 | M1 学習ループの検証 / M2 開く / M3 会計ならではの課題 |
| 2 利用者の獲得 | M4 3 級を通しで学べる・公開 |
| 3 知識共有の促進 | M5 定着と、聞ける・答えられる |
| 4 コミュニティによる共同開発 | M6 2 級と、書ける・直せる |
| 5 エコシステムの発展 | M7 競う・広がる |

### M1 学習ループを信じられる状態にする(進行中)
目的: 3 級の基礎テーマを会計 IDE で学べるようにし、教育方針を検証する。
進捗(2026-11-08): 実装項目は完了(図解ブロック 6 種、取引の流れのアニメーション、T 勘定タブ、オンボーディング、CI、匿名ユーザーの定期削除、5 テーマ 13 単元)。品質改善ループ(Monkey → Issue → 修正)で不具合を潰している段階。
- 残り: ユーザー自身による検証(`docs/testing-guide.md`)と調整。Monkey ラウンドで出た Issue のトリアージと修正。
- 完了条件: 検証結果が出て、教育方針を続けるか見直すか判断できる。

### M2 開く(目安 1 週。M1 の検証と並行してよい)
目的: 誰でも読め、複製でき、貢献できる形にする。機能は増やさない。
- 決める: 正式名称(残る唯一の未決。公開後の変更が高くつくので public にする前に決める)。ライセンスと公開時期は決定済み(ADR 0007)。
- 置く: `LICENSE`、コンテンツのライセンス表示、`CONTRIBUTING.md`(環境構築、単元の書き方、PR の通し方、禁止事項: 過去問転載・教科書転記)、`CODE_OF_CONDUCT.md`、Issue テンプレート(教材の誤り / 改善提案 / 不具合)、PR テンプレート(確認項目)、DCO の案内。
- つなぐ: 各単元のステップに「誤りを報告」「この単元を改善」(GitHub の Issue テンプレートと該当ファイルの編集画面へ、単元 ID とステップ番号を埋めて飛ぶ)。貢献者の表示は作らない(git 履歴と GitHub の contributors で足りる。2026-11-08 決定)。
- 公開する: リポジトリを public にする。公開 URL(VPS + Coolify)とプライバシーポリシーを置く。
- 完了条件: 外部の人が README だけで環境を立ち上げ、単元を 1 つ直す PR を出せる。

### M3 会計ならではの課題を増やす(目安 3〜4 週)
目的: ビジョン 4 章の学び方を課題の種類として実装し、各 1 単元で試す。人が使い続ける理由を作る。
- 課題の種類: バグ探し(debug)、同じ取引・別の方法(compare)、分岐(branch)、逆算(reverse)。
- 決算パイプライン: 仕訳帳 → 総勘定元帳 → 試算表 → 決算整理 → 精算表 → 財務諸表を段階ごとに見られる「決算」タブ。
- エンジン: 期を締める、評価勘定を含む開始残高、複数年のシナリオ。
- 完了条件: 4 種の課題がそれぞれ 1 単元で動き、反応(回答ログと感想)が記録されている。

### M4 3 級を通しで学べる・公開する(目安 6〜8 週)
目的: 3 級合格パスを 1 本通しで学べるようにし、外に向けて公開する。利用者の獲得を始める。
- コンテンツ: 3 級の残り全テーマ(固定資産の売却、資本と税金、決算整理、精算表、伝票・補助簿など)で合計 50 単元前後。執筆は AI の下書き + 人の査読で進め、ここで執筆ガイドとレビュー基準を実地で固める。
- 総合課題: 1 か月の会社を通して記帳し決算する「プロジェクト」単元。
- 模擬試験: CBT と同じ時間・構成の模試(パス固有)。修了証(自己申告の合格報告と合わせて)。
- 概念マップ: 前提・関連・対比を可視化し、学習済みを重ねる。
- レビューの基盤: コンテンツ PR のプレビュー環境(Coolify の PR デプロイ)。開発者でないレビュアーが実際に解ける。
- 周知: 公開の告知(Zenn の記事、X、簿記の学習コミュニティ)。運営者以外の利用者を初めて集める。
- 完了条件: テスターが 3 級パスを完走し模試で合格点を取れる。運営者以外からの Issue が立ち始めている。

### M5 定着と、聞ける・答えられる(目安 4〜6 週)
目的: 学習者ごとの状態に応じて支援し、学習中に生まれる質問を公共の知識に変える。
開始条件(コミュニティ部分): 週あたりの再訪者が継続的にいて、運営者以外からの報告・質問が月に数件以上ある。満たさない間は定着の項目だけ進める。
- 定着: 本登録(メール / Google)、デバイス間同期、学習ダッシュボード。間隔反復の復習キュー(誤解の出た課題と predict を優先)。同じ誤解が続いたら診断ステップを挟む「立ち止まり」。
- つまずきマップ: 課題ごとの初回正答率と誤解の分布、誤答パターンに無い誤答の多い課題を匿名で集計し公開する。閾値を超えた課題は Issue を自動で起票する(`type:content`)。
- Q&A: 単元・ステップに紐づく質問と回答。まず GitHub Discussions を単元から開く形で始め(作らない)、使われ方を見てから自前の実装を判断する。回答から Issue / PR へつなぐ導線を持つ。
- 保守者: 専門性のあるレビュアー(会計士・税理士・教員・実務者)を 2〜3 名、テーマの保守者として迎える。CODEOWNERS とレビュー基準(ビジョン 7.1)を文書にする。
- 完了条件: 復習と介入が動き再発率の指標が取れる。運営者以外が回答した質問と、外部の PR が統合された単元がある。

### M6 2 級と、書ける・直せる(目安 10〜12 週)
目的: 2 級範囲に広げつつ、学習者が発信し、教材を直せる場を作る。2 級以降の執筆量は 1 人では賄えない前提で、共同制作の仕組みをここで働かせる。
開始条件(共同制作部分): 外部の PR が継続して来ている。段 3(直す)で止まる人がいると観測できている。
- コンテンツ: 2 級商業簿記・工業簿記。テーマ軸の深さ 3 を埋める。保守者と AI の下書きで分担する。
- かたちで読む: 比例縮尺の貸借対照表・損益計算書。実在企業の決算(EDINET)を読み込み、形を比べ、「どの会社か」を当てる課題。
- サンドボックス: 自分の会社を開業し、1 年を運営して決算する。作った会社を共有できる(最初の「作品」の共有)。
- 記事: 解説記事・学習記録。Markdown を PR で置く形から始め、良い記事を単元や概念の解説へ昇格させる査読の流れを作る。自前のエディタは作らず、必要なら Zenn 等への連携で代替できるか先に確かめる。
- Web 編集: git を使わずに単元の文言を直して PR にできる編集画面(GitHub App 経由)。段 3 の壁が観測できた場合だけ作る。
- 完了条件: 2 級パスが通しで学べる。運営者以外が書いた単元が統合されている。

### M7 競う・広がる(以降)
- コンテスト: 自動採点の問題(逆算・バグ探し・総合問題)で期間限定に競う。ユーザー作問を受け付け、採用した問題は演習として残す。
- 1 級・公認会計士・税理士の理論パス、実務コース(確定申告、経理の月次)。深さ 4 は保守者が執筆・査読する。
- 学校・企業での利用: 自前ホストの手順(Docker Compose)と授業用パスの作り方を公開する。受講管理のような専用機能は作らない。
- 運営: 保守者会議、運営費の公開と GitHub Sponsors 等、必要なら法人格。
- 学習者向け AI 解説: 利用料の賄い方(スポンサー、持ち込みキー)が決まってから。教材作成・検証への AI 活用は M1 から継続する。

### 継続的に行うこと
- デザインの洗練: デザインシステム、図解とイラスト、ダークモード、アクセシビリティ。
- 性能と品質: Lighthouse、E2E の拡充、品質改善ループ、Skills / MCP の更新。
- コンテンツの改善: 回答ログとつまずきマップに基づく解説と誤答パターンの見直し。会計基準・税法・出題区分の改定の追従(単元の確認日)。
- 貢献者への対応: Issue と PR への返答を溜めない。CONTRIBUTING を実態に合わせて更新する。

## 3. v1 からの変更(維持・変更・削除)

| 項目 | 判断 | 理由 |
|---|---|---|
| 開発方針 1〜4、6 | 維持(3 と 6 は拡張) | content as code と計測は、そのまま貢献の受け皿と入口になる |
| 開発方針 5「個人開発として持続」 | 変更 → 「個人で始め、引き継げる形を保つ」 | 持続可能性の主体を個人からコミュニティへ移す |
| 開発方針 7 | 新設 | コミュニティ機能の先行投資を防ぐ |
| M1 学習ループの検証 | 維持 | 進行中。ビジョンの変更で中身は変わらない |
| M2 開く | 新設 | ライセンス・公開・貢献導線。小さい作業で、以降すべての前提 |
| 旧 M2 会計ならではの課題 | 維持 → M3 | 差別化の中核。利用者獲得の前に必要 |
| 旧 M3 3 級通し | 維持 + 公開と周知を追加 → M4 | 利用者獲得の段階と一体 |
| 旧 M4 定着と伴走 | 維持 + Q&A・つまずきマップ・保守者 → M5 | 「自分用の集計画面」を公開の集計に変更 |
| 旧 M4「AI 解説はサブスク時に再検討」 | 変更 → M7(費用の賄い方が決まってから) | 収益化と切り離す |
| 旧 M5 2 級と「かたちで読む」 | 維持 + 記事・Web 編集 → M6 | 2 級以降の執筆量は共同制作が前提 |
| 旧 M6「料金プラン(無料枠を維持)」 | 削除 | 収益化を目標にしない。運営費は寄付・スポンサーで検討 |
| 旧 M6「企業研修(チーム管理、進捗の見える化)」 | 変更 → 自前ホストと授業用パス | 専用機能ではなくオープンな構造で応える |
| 旧 M6「コミュニティ(作った会社・分析の共有)」 | 拡張 → M5〜M7 に分解 | 1 行の項目から段階的な計画へ |
| 「テスターは当面ユーザー自身」 | 変更 → M4 で運営者以外を集める | 公開そのものを検証にする |

- ライセンス: コード Apache 2.0、コンテンツ CC BY-SA 4.0、DCO(ADR 0007、2026-11-08 決定)。公開時期: M1 の検証後すぐ。正式名称: 未決。

- 収益化: 目標にしない。運営費の公開と寄付・スポンサーは M7 で検討する。
