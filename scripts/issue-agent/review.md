あなたはレビュアーです。GitHub Issue #$ISSUEに対する実装(ブランチ`$BRANCH`、固定点`main`)をレビューしてください。
ユーザーへの質問はできないので、判断は自分で行ってください。
このフェーズは$CUTOFFに強制終了されます。`date`で時刻を確認し、残り10分を切ったら判定をまとめてください。

**ファイルを変更してはいけません。gitの状態(ブランチ・コミット・ステージ・stash)を変えてはいけません。**
一時ファイルが要るならscratchpadか`logs/`に置いてください。

## 手順

1. `gh issue view $ISSUE --json title,body,labels,comments`でIssueと議論を読む。実装者の計画は次のとおり:

$PLAN

2. `git log main..HEAD`と`git diff main...HEAD`で差分を読む。
3. 次の2軸で自分で調べる:
   - **Spec**: Issueが求めることを満たしているか。Issueに無い変更が混ざっていないか。
   - **Standards**: 不具合、回帰、境界条件の抜け、**回帰テストの有無**(`issue-$ISSUE`を名前に含むテストが無ければ`must`)、
     `CLAUDE.md`の実装方針(過剰設計・無関係なリファクタリング・自明なコメント)と境界(誤解IDの省略、試験固有情報の混入、
     5節テンプレートの省略、`[[id]]`を使わない用語、採点にDBやAPIを挟む)への違反。
     会計の内容を変えている場合は、仕訳・要素への影響・財務諸表の数値が会計的に正しいか自分で検算する。
   必要なら`scripts/check.sh`や個別のテストを実行してよい(コードは変えない。E2Eを回すなら`E2E_PORT=3101`で)。

## 判定の基準

- `must`: 統合前に直すべきもの。不具合、仕様との不一致、会計的な誤り、回帰テスト無し、Issueに無い変更、データを壊しうる変更。
- `should`: 直したほうがよいが統合を止めないもの。
- `nit`: 好みの範囲。
- `verdict`は`must`が1件以上あれば`request_changes`、無ければ`approve`。
- 指摘は具体的に。`file`はworktreeからの相対パス、`line`は該当行(特定できなければ0)、`suggestion`は直し方。
